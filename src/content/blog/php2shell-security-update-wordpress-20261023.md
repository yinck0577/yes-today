全球廣泛使用的網站程式語言PHP爆發重大資安事件。PHP開發團隊於2026年10月21日緊急發布安全更新，修補兩項可能讓攻擊者在未經登入的情況下，遠端執行惡意程式的漏洞，兩者風險評分均達**CVSS v4.0的9.2分，屬於重大等級（Critical）**。

這次事件被資安研究人員稱為「PHP2Shell」，涉及CVE-2026-109618與CVE-2026-109619兩項PHP底層記憶體安全漏洞。除了遠端程式碼執行（Remote Code Execution，RCE），部分攻擊途徑還可能讀取伺服器記憶體中的密碼、驗證權杖及API金鑰。

更值得注意的是，漏洞在正式公開前就已出現攻擊活動。

亞馬遜旗下AWS於10月21日揭露，其MadPot威脅偵測系統最早在**10月17日**就觀察到PHP2Shell攻擊嘗試，比官方發布安全更新早了4天。Cloudflare與資安公司watchTowr也陸續回報相關攻擊流量及利用活動。

由於WordPress、Drupal、Joomla及大量企業網站都使用PHP，這次安全事件影響範圍廣泛。WordPress官方已呼籲網站管理員立即檢查PHP版本，但強調漏洞並非出在WordPress核心，因此單純更新WordPress外掛或佈景主題，無法修補問題。

目前PHP官方已發布8.2至8.5四個版本分支的安全更新。對網站管理員而言，除了立即安裝修補程式，也應檢查10月17日以來的伺服器紀錄，確認是否存在異常請求或入侵跡象。

## PHP2Shell是什麼？兩項PHP漏洞可能讓駭客遠端入侵

PHP是一種伺服器端程式語言，常用於處理網站登入、資料庫查詢、會員系統及動態網頁內容。

當使用者瀏覽PHP網站時，伺服器會依照請求執行相關程式，再將處理結果傳回瀏覽器。

這次漏洞發生在PHP本身的記憶體管理與錯誤處理機制，並非特定網站功能或外掛程式出錯。

PHP2Shell是資安界對這次漏洞事件使用的名稱，**不是第三項獨立漏洞**。目前公開的兩個主要漏洞編號，分別為CVE-2026-109618與CVE-2026-109619。

PHP Foundation指出，兩項漏洞在特定條件下，都可能讓未經身分驗證的攻擊者透過網路請求執行程式。

其中，Apache搭配mod_php的環境被認為風險尤其高。研究人員已證實，在部分預設設定下，攻擊者甚至能在網站應用程式開始執行前觸發漏洞。

不過，漏洞存在不代表每一種PHP伺服器配置都能使用相同方法成功攻擊，實際利用條件仍與PHP版本、執行環境及應用程式行為有關。

### CVE-2026-109618：記憶體不足造成資料損毀

第一項漏洞CVE-2026-109618，與PHP處理記憶體不足（Out of Memory，OOM）的方式有關。

當PHP執行網路請求時，如果記憶體使用量達到設定上限，程式可能被迫中止。

問題在於，若中止發生在內部資料尚未完成初始化的階段，PHP後續清理記憶體時，可能把不完整的資料誤認為有效內容，造成記憶體損毀。

研究人員已在Apache mod_php環境中證實，這項問題可能讓未經登入的攻擊者遠端執行程式。

資安公司Wiz還展示了另一種風險：在特定攻擊途徑下，攻擊者即使尚未取得遠端程式碼執行能力，也可能讀取PHP工作程序的記憶體。

這些記憶體內容可能包含密碼、登入驗證權杖、API金鑰等敏感資訊。

### CVE-2026-109619：釋放後使用造成安全風險

第二項漏洞CVE-2026-109619，涉及PHP在發生嚴重錯誤後，仍保留已失效的記憶體參照。

正常情況下，程式完成請求後，應釋放不再需要的記憶體。

但在特定錯誤處理流程中，PHP可能已經釋放某段記憶體，卻仍保留指向該位置的內部參照。

當同一個伺服器工作程序處理後續請求時，就可能再次使用已經失效的記憶體位置。

這類問題稱為「釋放後使用」（Use-After-Free），可能造成程式崩潰、記憶體損毀，甚至被利用來執行惡意程式。

PHP Foundation表示，研究人員已在實際PHP應用環境中證實相關遠端程式碼執行風險。

| 漏洞編號 | 核心問題 | 已證實的安全風險 | CVSS v4.0 |
|---|---|---|---|
| CVE-2026-109618 | 記憶體不足時，內部資料初始化與清理異常 | 遠端程式碼執行、記憶體資訊外洩 | 9.2 |
| CVE-2026-109619 | 錯誤處理後殘留已失效的記憶體參照 | 遠端程式碼執行、記憶體損毀 | 9.2 |

Wiz研究團隊已在測試環境中展示，這些漏洞可以影響WordPress、Drupal及Joomla等網站系統。

但問題根源位於PHP執行環境，因此不能將其視為單一內容管理系統的安全缺陷。

## PHP哪些版本有漏洞？8.2至8.5安全修補版本一次看

PHP官方於2026年10月21日發布四個安全修補版本，網站管理員應確認目前伺服器是否已安裝對應更新。

| PHP版本分支 | 官方修補版本 | 建議處理方式 |
|---|---|---|
| PHP 8.5 | **8.5.12** | 更新至8.5.12或更新版本 |
| PHP 8.4 | **8.4.27** | 更新至8.4.27或更新版本 |
| PHP 8.3 | **8.3.36** | 更新至8.3.36或更新版本 |
| PHP 8.2 | **8.2.35** | 立即修補，並規劃後續升級 |
| PHP 8.1及更早版本 | 已停止一般官方安全維護 | 優先升級至受支援版本，或確認供應商修補狀態 |

這些版本是PHP官方上游專案公布的安全修補版本。

若網站使用Linux發行版或企業長期支援服務提供的PHP套件，供應商可能採用「回溯修補」（Backport），將安全修正加入原有套件，而不直接變更主要版本號碼。

因此，部分網站即使顯示較舊的PHP版本號，也可能已安裝供應商提供的安全修補。是否完成更新，仍須以作業系統或主機商的安全公告為準。

### PHP 8.1還能用嗎？8.2何時停止支援？

PHP 8.1已經結束官方安全支援，不建議繼續作為公開網站的長期執行環境。

針對這次重大漏洞，PHP安全團隊特別提供PHP 7.4、8.0及8.1的最小化原始碼回溯修補，協助自行編譯PHP或缺乏長期支援供應商的使用者處理問題。

但這不代表上述舊版本恢復正常維護，也不代表所有更早的PHP版本都有官方修補程式可直接下載。

至於PHP 8.2，官方安全支援將於**2026年12月31日結束**。

因此，使用PHP 8.2的網站，即使已更新至8.2.35，仍應開始評估升級至PHP 8.3、8.4或8.5。

另外，PHP 8.6目前仍處於測試階段，不應為了修補漏洞而將正式營運網站直接切換至尚未正式發布的候選版本。

## WordPress網站會受影響嗎？如何查詢PHP版本與更新

WordPress是全球廣泛使用的內容管理系統，主要以PHP作為伺服器端程式語言。

因此，只要網站運作於受影響且尚未修補的PHP環境，就可能面臨PHP2Shell帶來的安全風險。

WordPress官方於10月21日發布安全提醒，要求網站管理員立即確認PHP更新狀態。

不過，官方也明確指出，這次漏洞並非WordPress本身的問題，因此不需要為此另外發布WordPress核心修補版本。

**更新WordPress核心，不等於更新PHP。**

WordPress、外掛與佈景主題屬於網站應用程式；PHP則是負責執行網站程式的伺服器環境。

即使WordPress已經更新至最新版本，只要底層PHP仍未修補，就不能認定網站已經排除PHP2Shell風險。

### WordPress後台查詢PHP版本教學

WordPress管理員可以直接從網站後台查詢目前使用的PHP版本。

操作路徑如下：

**WordPress後台 → 工具（Tools）→ 網站狀態（Site Health）→ 資訊（Info）→ 伺服器（Server）→ PHP版本**

如果使用虛擬主機或代管服務，也可以登入主機商提供的管理控制台，確認PHP版本及安全更新狀態。

但要注意，WordPress後台主要提供版本查詢功能，通常不能直接透過這個頁面完成PHP升級。

實際更新PHP，通常需要在主機商控制台操作，或由伺服器管理員安裝安全套件。

若主機商表示已完成修補，但WordPress仍顯示較舊版本，應確認是否採用回溯修補，而非只根據版本號碼判斷。

### 為什麼更新WordPress外掛還不夠？

因為PHP2Shell漏洞存在於PHP執行環境。

更新WordPress外掛或佈景主題，可以修補這些應用程式本身的問題，但無法直接修正PHP底層的記憶體管理漏洞。

如果網站由主機商代管，應優先詢問主機商是否已套用PHP2Shell安全修補。

若主機商尚未提供更新時間，也應確認是否有臨時防護措施，以及是否需要限制部分網站功能或外部存取。

## PHP2Shell已被駭客利用嗎？AWS發現10月17日就有攻擊嘗試

PHP2Shell的威脅已經超出研究人員在測試環境中展示漏洞的階段。

AWS於2026年10月21日公布，旗下MadPot威脅偵測系統最早在10月17日，就觀察到疑似利用PHP2Shell的攻擊嘗試。

這次攻擊發生在漏洞正式公開前4天，當時PHP安全團隊仍在準備修補版本。

AWS指出，10月17日的攻擊來源使用商業匿名網路服務。由於當時漏洞資訊尚未正式公開，這項活動顯示可能已有外部人士掌握相關攻擊資訊。

但AWS也表示，目前仍不清楚攻擊者如何在正式揭露前取得漏洞利用方法。

到了10月21日，AWS又觀察到更多針對MadPot蜜罐系統的攻擊嘗試，來源及攻擊內容有所差異，顯示可能有不只一組攻擊者參與。

官方修補程式發布後，相關概念驗證程式也迅速出現，攻擊活動隨之增加。

### Cloudflare與watchTowr也觀測到攻擊活動

Cloudflare於10月21日表示，已觀察到攻擊者嘗試利用PHP2Shell攻擊客戶網站。

Cloudflare指出，攻擊者持續調整惡意請求內容，試圖繞過既有防護規則。

為此，Cloudflare在漏洞正式揭露前就開始部署網站應用程式防火牆（Web Application Firewall，WAF）防護，並於10月21日將相關規則提供給使用WAF的免費及付費方案客戶。

資安公司watchTowr也表示，其Attacker Eye全球蜜罐網路已觀察到CVE-2026-109618與CVE-2026-109619的實際利用嘗試。

不過，必須區分以下兩種情況。

**攻擊嘗試已被觀測，不代表所有受攻擊網站都已成功遭到入侵。**

AWS表示，部分觀測到的攻擊是否能在真實網站環境中成功，仍有待確認。

不同資安公司的偵測系統、觀測範圍及判斷標準也不完全相同，因此不能直接將攻擊流量數量視為成功入侵的網站數量。

但對網站管理員而言，這些報告已足以說明，不能只等待更多受害案例出現才進行更新。

## PHP漏洞2024年就有線索？官方坦承修補延誤

PHP2Shell事件另一個受到關注的焦點，是其中一項漏洞的早期線索，早在2024年就已經被發現。

根據PHP Foundation於10月21日公布的說明，PHP在2024年接受多年來首次外部安全稽核，由Quarkslab執行。

在修補稽核發現的其他問題時，一名PHP核心開發者察覺到記憶體不足處理機制可能存在風險。

當時研究人員已推測，這個問題可能被用於攻擊，但尚未找到明確的利用途徑。

PHP安全團隊曾討論多種修補方案，卻面臨相容性、效能及第三方擴充套件可能受影響等困難。

由於PHP被大量網站與軟體使用，修改底層記憶體管理方式可能造成廣泛影響，團隊遲遲無法決定採用哪一種修補方式。

PHP Foundation坦承，這項延誤反映安全團隊的決策流程及人力資源存在結構性問題。

不過，2024年發現的是潛在風險線索，並非當時就已經掌握完整、可實際執行的遠端攻擊方法。

### 10月20日提前洩漏，為何緊急發布修補？

PHP Foundation原本計畫於2026年10月22日發布安全修補。

但10月20日，兩項漏洞的CVE編號提前在網路論壇與社群平台流傳，當時甚至出現錯誤的CVSS 10.0評分。

PHP Foundation澄清，官方最終確認的風險評分為9.2，而且最初流傳的資訊並未包含完整技術細節。

不過，漏洞編號曝光後，相關研究影片及概念驗證資訊陸續流傳，增加攻擊者研究漏洞的可能性。

因此，PHP團隊決定將原訂10月22日的正式修補，提前至10月21日發布。

這項決定也必須兼顧軟體供應商的準備時間。

如果立即公開漏洞，卻沒有讓Linux發行版、主機商及其他供應商取得可安裝的修補套件，網站管理員可能反而面臨知道漏洞存在、卻無法立即更新的情況。

最終PHP於10月21日發布四個安全版本，並要求所有使用PHP處理網站請求的管理員盡快更新。

### AI如何協助發現PHP漏洞？Calif、OpenAI與Wiz參與研究

這次事件也凸顯AI工具在資安研究中的新角色。

PHP Foundation指出，2026年7月30日，資安公司Calif在OpenAI「Patch the Planet」計畫下，開始進行PHP安全稽核。

8月11日，Calif研究人員Ryan A回報了一項遠端程式碼執行漏洞，其根本原因與2024年發現的記憶體不足問題相同。

OpenAI也獨立回報相同根本原因，並於9月18日提出其他攻擊途徑。

Wiz則於8月24日向PHP安全團隊回報相關漏洞研究結果。

根據Wiz公布的技術報告，研究團隊使用多種AI工具協助分析程式碼、尋找攻擊途徑、驗證漏洞及測試修補效果。

這些工具有助於研究人員分析複雜的記憶體狀態，並在不同PHP版本與執行環境中反覆測試。

PHP Foundation也表示，團隊已導入AI輔助工具，用於分類安全報告、辨識重複問題及驗證漏洞。

不過，AI協助找出問題，不代表能自動完成安全修補。

PHP Foundation指出，最困難的工作仍包括維持程式相容性、避免造成新的效能或安全問題，以及確保不同PHP版本與第三方擴充套件都能正常運作。

最終修補方案的判斷、程式修改及發布決策，仍由開發人員負責。

這次研究也讓PHP安全團隊更清楚看到漏洞的實際危害。原本在2024年尚未找到完整攻擊方法的記憶體問題，到了2026年已能透過研究人員與AI輔助工具，證實可能造成遠端程式碼執行及敏感資訊外洩。

## PHP網站管理員現在該怎麼辦？5項安全檢查

對使用WordPress、Laravel、Drupal、Joomla，或自行開發PHP網站的管理員而言，目前最重要的工作，是確認正式營運環境已安裝修補，並檢查是否存在先前遭到攻擊的跡象。

### 1. 確認網站實際執行的PHP版本

先檢查正式網站目前使用的PHP版本，而不只是開發電腦或測試環境。

如果網站由主機商代管，應查看主機控制台或直接詢問服務商。

若自行管理伺服器，則應確認實際處理網站流量的PHP執行環境與套件狀態。

### 2. 安裝對應安全修補版本

使用PHP官方上游版本的網站，應更新至8.5.12、8.4.27、8.3.36或8.2.35，或更新的安全版本。

如果使用Linux發行版提供的PHP套件，則應依照供應商安全公告安裝修補。

對於已停止官方維護的PHP 8.1及更舊版本，應優先規劃升級。

### 3. 更新前備份，並測試網站功能

更新PHP前，應依網站規模備份程式、資料庫與重要設定。

更新完成後，確認登入、表單、付款、檔案上傳、資料庫查詢等功能是否正常。

使用客製化外掛或較舊程式框架的網站，也應檢查與新版PHP的相容性。

### 4. 確認伺服器已實際載入修補版本

安裝新版PHP套件後，仍須確認網站使用的服務已正確重新載入。

例如PHP-FPM、Apache或其他PHP執行環境，可能需要依照系統管理文件重新啟動或重新載入。

如果服務仍使用更新前的工作程序，即使套件已經安裝，也可能尚未真正套用修補。

### 5. 檢查10月17日以來的異常紀錄，確認是否已有入侵跡象

由於AWS最早在10月17日就觀察到攻擊嘗試，網站管理員不應只檢查10月21日漏洞正式公布後的紀錄。

建議至少回溯檢查10月17日以來的相關資料，包括：

- 異常的HTTP POST請求，尤其是可疑的表單與檔案上傳流量。
- PHP工作程序頻繁崩潰、異常重新啟動，或大量HTTP 500錯誤。
- 伺服器出現不明程序、異常檔案修改或可疑的新增檔案。
- 網站管理帳號、驗證資訊及重要設定是否出現非預期變動。

AWS特別提醒，網站管理員應留意與PHP檔案上傳進度處理相關的可疑請求。

不過，單一異常請求或HTTP 500錯誤並不能直接證明網站已遭入侵，仍須結合伺服器紀錄與其他證據判斷。

若發現疑似入侵，應保留相關紀錄，並依事件應變程序調查受影響範圍。

必要時，還應檢查是否存在惡意檔案、後門或遭外洩的憑證，並在確認影響後進行適當的金鑰與密碼輪替。

**安裝安全修補可以阻止漏洞繼續被利用，但不代表能自動清除攻擊者先前留下的惡意程式。**

## PHP漏洞常見問題FAQ

### Q1：PHP 8.5.11有漏洞嗎？

有。

PHP官方於2026年10月21日發布8.5.12，修補PHP2Shell相關漏洞。

若網站仍使用PHP 8.5.11或同一分支更早版本，應立即更新，或確認系統供應商是否已提供回溯修補。

### Q2：WordPress更新到最新版，就安全了嗎？

不能只根據WordPress版本判斷。

這次漏洞位於PHP執行環境，必須確認伺服器上的PHP已完成安全修補。

WordPress官方也明確表示，這次事件不需要另外發布WordPress核心更新。

### Q3：主機商說已修補，但PHP版本號沒變，正常嗎？

有可能。

部分Linux發行版及企業長期支援服務會使用回溯修補方式，將安全修正套用至既有套件版本。

因此，應向主機商確認修補公告、套件版本及更新紀錄，而不是只看PHP主要版本號碼。

### Q4：網站有Cloudflare或WAF，就不用更新PHP嗎？

仍然需要更新。

Cloudflare已部署針對PHP2Shell的WAF防護，但官方也強調，這些措施屬於額外防護，不能取代PHP本身的安全修補。

PHP官方指出，目前沒有任何單純依靠設定調整，就能完整解決這兩項漏洞的方法。

### Q5：PHP更新完成後，還需要檢查是否遭入侵嗎？

需要。

因為AWS已經觀察到漏洞正式公開前的攻擊嘗試，不能排除部分網站在修補前曾經受到攻擊。

即使目前PHP版本已更新，也應檢查近期網站與伺服器紀錄，確認是否有異常程序、可疑檔案或憑證遭竊跡象。

### Q6：一般網站訪客需要更新PHP嗎？

通常不需要。

PHP主要是在網站伺服器上執行，一般訪客不需要在手機或電腦瀏覽器中另外更新PHP。

需要處理的是網站經營者、主機商、系統管理員及負責維護PHP應用程式的開發團隊。

## PHP2Shell事件揭露什麼問題？AI加速漏洞研究，也考驗開源安全維護

PHP官方已在10月21日提供四個受支援分支的安全修補版本，但這次事件並未隨著更新發布就完全結束。

AWS、Cloudflare及watchTowr已經觀察到相關攻擊活動，代表網站管理員除了安裝修補，也需要檢查先前是否出現可疑行為。

另一方面，PHP Foundation承認，2024年就已發現的潛在記憶體問題，因修補方案難以取得共識、人力不足及相容性疑慮，延宕至2026年才完成修正。

AI工具則讓研究人員更有效率地分析這類複雜漏洞，協助驗證不同攻擊途徑，也讓原本需要大量專業時間才能完成的測試更容易進行。

但這些能力同樣可能被攻擊者利用。AWS指出，AI輔助分析降低了研究與調整攻擊程式的成本，使漏洞公開後到出現攻擊活動之間的時間進一步縮短。

對網站經營者而言，這次事件最直接的提醒，是安全維護不能只停留在WordPress後台的外掛更新通知。

PHP版本、伺服器套件、安全支援期限，以及實際的系統紀錄，都應納入網站的定期維護範圍。

目前最優先的工作仍是確認PHP已完成修補；如果網站曾在10月17日之後使用受影響版本對外提供服務，也應進一步檢查是否存在入侵跡象。
